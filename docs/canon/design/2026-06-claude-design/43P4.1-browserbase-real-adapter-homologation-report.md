## 1. Docs oficiais consultadas
- `https://docs.browserbase.com/reference/api/create-a-session` — `POST https://api.browserbase.com/v1/sessions`, header `X-BB-API-Key`, body `{ projectId }` (inferível da key). Resposta: `id`, `connectUrl` (WebSocket p/ Playwright `connectOverCDP`), `signingKey`, `status` (PENDING/RUNNING/COMPLETED/...), `region`, `expiresAt`.
- `https://docs.browserbase.com/introduction/what-is-browserbase` — plataforma de cloud browsers para agentes; uma API key; sessões isoladas.
- **Decisão de segurança:** `connectUrl` e `signingKey` contêm credencial/token → **nunca** são propagados ao caller/frontend. O adapter captura só `id/status/region/expiresAt`.

## 2. Envs necessárias
`BROWSERBASE_API_KEY` e `BROWSERBASE_PROJECT_ID` (no EasyPanel, server-side). Sem elas → `evaluateBrowserbaseReadiness` bloqueia (`browserbase_api_key_missing`/`browserbase_project_id_missing`) e **nenhuma rede** é chamada.

## 3. Como o browser real é bloqueado (falha fechado)
`evaluateBrowserbaseReadiness` exige **simultaneamente**: env (api_key+project_id) + `GLOBAL_KILL_SWITCH=false` + `PORTAL_REAL_ACTION_ENABLED` + `PORTAL_LOGIN_REAL_ENABLED` + `PORTAL_SESSION_CAPTURE_ENABLED` + **`BROWSERBASE_REAL_BROWSER_ENABLED`** + **approval humano**. Faltando qualquer um → `can_open_real_browser=false`. `createBrowserbaseLoginSession` **só chama o transport (rede) se `can_open_real_browser`** — caso contrário retorna `blocked` sem tocar a rede (provado em teste: transport spy com 0 chamadas).

## 4. Como o canary funciona
Quando (no futuro) as flags + env + approval estiverem ligados, `login-setup/start` com `mode='real_canary'` poderá abrir **uma** sessão Browserbase real controlada (`createBrowserbaseLoginSession`), entrando em `browser_opened → waiting_human_login`. **O sistema não faz login**: ele só abre o browser; o **humano** digita as credenciais. Hoje (flags off) o canary fica bloqueado; `login-setup/start` já retorna `browserbase_readiness` no payload para diagnóstico.

## 5. Como o humano fará login / SessionRef
1. Admin liga as flags + dá approval (ato deliberado).
2. `real_canary` abre a sessão Browserbase real (live view).
3. O **corretor** faz login uma vez (e resolve CAPTCHA/2FA — sempre HITL, nunca bypass).
4. O storageState é persistido **criptografado no Vault**; o sistema guarda só uma **`storage_ref` opaca** (43P4 `captureSessionRef`), nunca cookies/headers.
5. `complete` → `session_captured → session_verified`; a SessionRef mascarada é anexada à conta.
6. Health-check por metadados; expirou → novo login assistido.

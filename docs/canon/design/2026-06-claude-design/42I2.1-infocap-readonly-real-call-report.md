> **Status:** concluído · `py_compile` verde · typecheck verde · build verde · `git diff --check` limpo · **backend Python + adapter TS** (sem SQL/migration, sem RAG/LLM para cobertura, sem WhatsApp/dispatch, sem segredo/CPF em response/log/diagnostics, sem credenciais commitadas) · sem deploy automático.
> **Data:** 2026-06-15 · **Modelo:** Claude Opus 4.8 · **Branch:** main

## 1. Spec real obtida (CorpAPI / InfoCap)
Da doc Postman do Founder (`api.corpnuvem.com`):
- **Auth:** `POST /login` body `{"email","senha","aplicacao":0}` → token; usado como header `Authorization: <token>`.
- **Busca cliente:** `GET /lista_clientes?texto=<termo>` → lista de clientes. (Também existem `/cliente`, `/documento?codfil&nosnum`, `/producao?texto`, `/renovacoes`.)
Implementação inicial usa **login → /lista_clientes?texto=<documento|nome>** (read-only). Paths/param são **configuráveis** via `connection_config` (`infocap_auth_path`, `infocap_search_path`, `infocap_search_param`) sem mudança de código.

## 2. Arquivos alterados/criados

## 3. Endpoints usados
- **Web→Backend (interno):** `POST {BACKEND}/attendance/connectors/infocap/lookup` (header `X-AutoBrokers-Internal-Key`).
- **Backend→InfoCap:** `POST {base_url}/login` + `GET {base_url}/lista_clientes?texto=` (read-only).
- **Cliente→Web:** `POST /api/attendance/cases/[caseId]/runtime/policy-lookup { source:'infocap', mode:'connector' }` (inalterado; já existia).

## 4. Como decifrou com segurança
O **backend** lê `tenant_connections.encrypted_secret_ref` e decifra com `EncryptionService` (Fernet, `ENCRYPTION_KEY` só no backend) → `{username/email, password/senha}`. O segredo **nunca** trafega pelo Web, **nunca** é logado, **nunca** retorna em response/diagnostics. O Web só chama o backend com a chave interna (Next↔Backend), sem acesso ao segredo.

## 5. Como chamou InfoCap (read-only)
`httpx.AsyncClient(timeout=12s, base_url)`: (1) `POST /login` `{email,senha,aplicacao:0}` → token (extrai de `token`/`access_token`/`jwt`/… ou corpo string); (2) `GET /lista_clientes?texto=<documento(dígitos)|nome>` com `Authorization`. **Nenhuma** escrita/ação externa; só consulta.

## 6. Normalização de estados
- `auth` 401/403 → `auth_error`; `auth` ≥400 → `provider_error`; sem token → `auth_error`.
- `search` 404 / lista vazia → `not_found`; 401/403 → `auth_error`; ≥400 → `provider_error`; timeout/rede → `provider_error`.
- exatamente 1 → `found`; >1 → `multiple_matches` (até 5 matches mascarados, `requires_human=true`).
- conexão ausente/sem base_url → `blocked_not_configured`; sem credenciais → `blocked_missing_credentials`.

## 7. found → evidência (verified_by_connector)
`found` retorna `selected` **sanitizado** (sem CPF/payload bruto): `policy_ref`, `insurer_key?`, `product?`, `policy_status?`, `masked_policy_number` (só 2 últimos), `holder_name_masked` (iniciais). `coverage_evidence` estruturado (`source:'infocap'`, `verified_by:'connector'`, `confidence:'medium'`, `coverage_summary`, `limitations`). O Web mapeia para `PolicyLookupResult{ source:'connector', verification_status:'verified_by_connector' }` e persiste via `persistPolicyLookupResult` → `policy_source='connector'`, `coverage_evidence`, `verification_status='verified_by_connector'`, `macro_state='policy_evidence_ready'`. **`not_found`/`multiple`/`provider_error`/`auth_error`** → **não** confirma cobertura, **não** cria evidência fake, **não** vira `policy_evidence_ready`.

## 8. Mock/manual preservados
`source:'mock'` e `source:'manual'` continuam idênticos (mesma validação/persistência via `persistPolicyLookupResult`). Apenas `source:'infocap'` foi ligado à chamada real.

## 9. Logs / sanitização
Backend loga só `company`, `connection`, `provider`, `status`, `duration_ms` — **nunca** documento/login/senha/token/ciphertext/payload. Web não loga document/secret. Resposta pública e diagnostics sem CPF/segredo.

## 10. Como testar
**Pré-req:** backend deployado (`ENCRYPTION_KEY`, `BACKEND_INTERNAL_API_KEY`/`ADMIN_API_KEY`); conexão InfoCap `ready_for_real_lookup=true` (42I2.0B/0C: base_url + credenciais gravadas); caso em `policy_lookup_required` com `insured_document_ref`.
```js
await (await fetch('/api/attendance/connectors/infocap/diagnostics')).json(); // ready_for_real_lookup:true
const r = await fetch(`/api/attendance/cases/${caseId}/runtime/policy-lookup`, {
  method:'POST', headers:{'Content-Type':'application/json'},
  body: JSON.stringify({ source:'infocap', mode:'connector' })
});
console.log(r.status, await r.json());
```
**Esperado:** `found` → `verification_status='verified_by_connector'`, `macro_state='policy_evidence_ready'`, `selected` mascarado, `external_action.sent=false`. `not_found`/`multiple` → caso permanece sem confirmar cobertura. **mock** continua funcionando.

## 11. Limitações
- A busca usa `/lista_clientes?texto=` (cliente). Se o `texto` não casar por CPF na CorpAPI, ajustar `infocap_search_path`/`infocap_search_param` em `connection_config` (ex.: `/producao`) sem mudar código. A normalização de campos é defensiva (extrai array de chaves comuns); pode precisar de ajuste fino por response real (42I3).
- `coverage_evidence` confirma que o segurado/apólice **existe** (read-only); a interpretação de cobertura específica do serviço fica para o **42I3 (Policy Evidence Normalizer)**.
- Não validado contra a API real neste ambiente (sem deploy/credenciais aqui); validado por contrato/typecheck/build.

## 0. Por que o teste do 42W1 falhou (e o que corrigi)
O teste retornou `ok:false` + só `conversation_id` em todas as mensagens. Diagnóstico: o bridge orquestrava via **self-fetch HTTP** (`fetch(request.nextUrl.origin + '/api/...')`) — Next chamando a própria origem. Em produção isso falha (deployment protection / resolução de origin); a resposta vinha vazia (não-JSON) → `bridge.json = {}`. O middleware **não** era a causa (ele libera `/api/*`). **Correção:** troquei TODO self-fetch por **invocação in-process** dos route handlers (`lib/attendance/runtime-invoke.ts`) — sem rede, mais rápido e robusto. O backend→bridge (FastAPI→Next) continua HTTP (necessário, cross-service), mas os saltos Next→Next agora são in-process.

## 1. Hardcodings removidos do canal WhatsApp
Antes (nichado em Allianz/Residencial/Eletricista): `inferSubcorridorFromText` sempre `electrician`; no create do case, `corridor_key='allianz_residential_assistance'`, `insurer='allianz'`, `line='residential'`, `macro='residential_assistance'`, summary fixo. **Agora**: o canal não decide corredor — um **resolver global** classifica a intenção e mapeia para um corredor **vindo de `corridor_templates`** (que já carrega `insurer_key`/`line_kind`/`macro_service`/`service_type`). Sem template → **triagem**. Nenhum `allianz/residential/electrician` hardcoded no canal.

## 3. Resolver global (`resolveAttendanceIntentAndCorridor`)
Classifica buckets: `residential_assistance`, `auto_assistance`, `claim`, `policy_question`, `policy_consultation`, `followup_existing_case`, `billing_document`, `unknown` (prioridade followup > claim > policy > billing > auto > residential). Mapeia o bucket para um corredor **entre os `availableCorridors`** (global + tenant; **tenant prioriza global**). Saída: `confidence`, `intent`, `insurer_key/line_kind/macro_service`, `selected_corridor_key/subcorridor_key`, `needs_clarification`, `clarification_question`, `candidate_corridors`. Sem corredor → triagem.

## 4. corridor_templates como fonte operacional
O bridge carrega `corridor_templates` ativos (`company_id is null` OR `= company`) e passa ao resolver. O case é criado com os campos **do template** (insurer/line/macro/corridor/sub). O `corridor_run` só nasce se houver template real (sem run falso em triagem). Adicionar um novo corredor = inserir um `corridor_template` ativo — **sem tocar no WhatsApp**.

## 5. Triagem (intenção sem corredor)
- **Criação**: intenção desconhecida/sem template → case `status='triage'`, `intent` do bucket, corredor null, `next_step` = pergunta esclarecedora; **sem run**. Responde humano.
- **Upgrade**: quando um case em triagem recebe nova mensagem que casa um corredor → o bridge atualiza o case (campos do template + `collecting_slots`), cria o run e segue o intake. Se ainda não casar → re-pergunta.

## 6. Fallback MVP por env (sem default invisível)
`ATTENDANCE_DEFAULT_CORRIDOR_KEY` + `ATTENDANCE_DEFAULT_SUBCORRIDOR_KEY` (opcionais). Só são usados se **configurados E o corredor existir** entre os disponíveis. Sem eles, intenção desconhecida → triagem (comportamento global correto). Para o MVP atual, configurar esses envs faz "Oi" cair direto no corredor residencial; sem eles, "Oi" pede esclarecimento e "estou sem luz" faz o upgrade.

## 7. Fluxo Allianz Residencial / Eletricista preservado
"estou sem luz", "disjuntor caiu", "sem energia na cozinha" → bucket `residential_assistance` → casa o template `allianz_residential_assistance/electrician` (line=residential + macro assist) com **confidence high** → cria case + run e segue o intake idêntico ao dashboard. Verificado nos testes.

## 8. Outros intents (preparados, sem inventar execução)
`auto/pneu`→auto_assistance, `bati o carro`→claim, `consultar apólice`→policy_consultation, `tenho cobertura?`→policy_question, `previsão do prestador?`→followup, `boleto`→billing. Sem template para esses ainda → **triagem** com pergunta humana e `candidate intent` registrado em `metadata.resolved_intent`. **Nunca** viram residencial/Allianz por engano (teste cobre isso).

## 9. Continuação / followup
`followup_existing_case` não cria corredor: o routing já reusa o case aberto (`reply_existing`) quando existe; followup sem case abre triagem perguntando de qual atendimento se trata.

## 10. Como adicionar um novo corredor (sem mexer no WhatsApp)
1. Inserir um `corridor_template` ativo com `corridor_key/subcorridor_key/insurer_key/line_kind/macro_service/service_type/required_slots`. 2. (Opcional) ajustar as regex de `classifyAttendanceIntent` se a intenção tiver vocabulário novo. 3. Pronto — o resolver passa a rotear para ele. O canal WhatsApp não muda.

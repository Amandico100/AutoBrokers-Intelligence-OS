## 1. Diagnóstico do teste do Founder (o que aconteceu)
O teste real chegou na rota e chamou `source:'infocap'`, mas voltou `ok:false` / `unverified` / `policy_source:unknown` / `coverage:{}` / `macro:policy_lookup_required`, e o `next_step` ficou com o texto obsoleto do gate de identidade ("lookup será implementado no próximo batch"). **Causa raiz provável:** a busca usava `GET /lista_clientes?texto=<CPF>`, mas na CorpAPI `/lista_clientes?texto=` é **busca por NOME** — buscar por CPF ali retorna vazio → `not_found`. A doc Postman tem o endpoint correto de CPF: **`GET /busca_cpf?cpf_cnpj=<dígitos>`** (e `/cliente_cpf?codfil=1&cpf_cnpj=`). Também faltava diagnóstico seguro para distinguir `not_found`/`auth_error`/`provider_error`.

## 2. Correções aplicadas
1. **Estratégia de busca correta (CorpAPI):** com documento → `GET /busca_cpf?cpf_cnpj=<dígitos>` (`query_strategy='document_cpf'`); sem documento → `GET /lista_clientes?texto=<nome>` (`query_strategy='customer_name'`). Tudo **configurável** via `connection_config` (`infocap_cpf_search_path`/`infocap_cpf_search_param`/`infocap_search_path`/`infocap_search_param`/`infocap_search_extra_params`) sem mudar código.
2. **Normalização real dos campos** (de `/documento`/`busca_cpf`): `numapo`→nº apólice (mascarado), `cliente`→nome (mascarado), `seguradora_abrev`→seguradora, `ramo_abrev`→ramo, `sit_acompanhamento_txt`/`cancelado`→status, `codcli`→ref.
3. **Diagnóstico sanitizado** no `policy_lookup_result`: `status`, `provider`, `query_strategy`, `search_path`, `search_param`, `http_status`, `result_count`, `blockers`, `notes`, `matches` (mascarados). **Nunca** CPF/login/senha/token/payload.
4. **next_step corrigido** (não mais obsoleto): mensagem segura por status (auth_error / multiple_matches / blocked / genérico) — persistida no caso e no run.
5. **Sem found não persiste cobertura:** `verification_status` continua `unverified`, `policy_source` não vira `connector`, `coverage_evidence` não é criado, `macro_state` continua `policy_lookup_required`, `external_action.sent=false`.
6. **multiple_matches:** até 5 matches mascarados + `requires_human=true`; não escolhe sozinho.

## 6. Como interpretar o próximo teste (decisão)
- **`not_found` com `query_strategy=document_cpf`** e CPF real válido → ajustar `infocap_cpf_search_path`/param (testar `/cliente_cpf?codfil=1&cpf_cnpj=` via `connection_config.infocap_cpf_search_path='/cliente_cpf'` + `infocap_search_extra_params={"codfil":1}`), ou validar formato do CPF aceito.
- **`auth_error`** → o login não retornou token no formato esperado, ou credenciais inválidas → revisar `encrypted_secret_ref`/email-senha no Vault (regravar via `/secret`). Pode ser necessário ajustar `infocap_token_field` em `connection_config` se o campo do token for específico.
- **`provider_error` (http_status)** → endpoint/headers; ajustar via config.
- **`found`/`multiple_matches`** → seguir para 42I3 (normalizar evidência/escolha).

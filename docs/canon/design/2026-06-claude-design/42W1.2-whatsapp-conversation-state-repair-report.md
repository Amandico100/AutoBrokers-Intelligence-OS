## 1. Causa raiz de cada bug
- **P0 (re-pedia apólice após selecionar):** o interceptor de seleção só checava `metadata.policy_lookup.status==='multiple_matches'`. Esse marcador **não** é limpo pelo policy-select; e o interceptor não olhava se a apólice já estava verificada. Então toda mensagem seguinte caía na seleção.
- **P1 (`selected_subcorridor_key=null`):** existem **dois** templates `allianz_residential_assistance` no seed — o **nível-família** (`subcorridor_key=null`) e o **eletricista** (`electrician`). O `matchCorridor` pegava o primeiro match (família) → subcorridor null.
- **P1b (ordem de mensagens):** resposta tardia de risco ("não tem cheiro de queimado") no gate de CPF caía em `extractDocument` → "CPF inválido".
- **P2:** após o select o bridge não chamava `step`, então não fazia a próxima pergunta operacional.

## 3. Como corrigi a finalização da seleção (P0)
`isPolicySelectionAlreadyResolved(case)` retorna true se: `policy_source==='connector'`, `verification_status∈{verified_by_connector,verified_by_human}`, `policy_snapshot.policy_ref`, `coverage_evidence.source/verified_by==='connector'`, ou `metadata.policy_selection_status==='resolved'`/`selected_policy_ref`/`policy_select.selected_policy_ref`. O bridge **só** intercepta como seleção quando há `multiple_matches` **E** `!isPolicySelectionAlreadyResolved`. Após o select por WhatsApp, gravo marcadores explícitos em `metadata` (`policy_selection_status='resolved'`, `selected_policy_ref/at/by/strategy`). Resultado: depois de "a primeira", "é na cozinha" segue como slot — **não repete a lista**.

## 4. Como corrigi a pergunta pendente / ordem (P1b)
No gate de identidade, se o documento é inválido **e** a mensagem casa um padrão de risco-tardio (`não tem cheiro de queimado`, `sem faísca`, `sem risco`…), respondo humano: *"Perfeito, obrigado por confirmar que não há sinal de risco. Agora, para localizar a apólice, pode me enviar só os números do CPF do segurado?"* — em vez de "CPF inválido". Guardado (só dispara para documento inválido + linguagem de risco), não afeta o dashboard (que envia CPF válido no gate). No webhook real o buffer/debounce já consolida as mensagens fragmentadas; isto é a rede de segurança para fora de ordem.

## 5. Como corrigi o subcorridor (P1)
`matchCorridor` agora pontua candidatos: **tenant (+100)**, **casa a sub-intenção** por `subcorridor_key`/`service_type` (+40), **subcorredor não-nulo/operacional** (+10). "sem luz/disjuntor" → sub-intenção `electrician` → escolhe o template `electrician` (não a família). O `corridor_run` nasce do template correto. Teste cobre inclusive ordem invertida do array.

## 6. Continuar após seleção (P2)
Após policy-select OK, o bridge: insere a confirmação ("Perfeito, selecionei a apólice com final ****99. Ela está vigente.") → chama `step` (resume: mensagem de cobertura + próximo slot) → `maybePrepareDispatchDraft`. `auto_reply` = confirmação + próxima pergunta. O cliente nunca fica sem pergunta operacional.

## 7. Dispatch draft pós-slots
`maybePrepareDispatchDraft` roda após o select e nos slots seguintes (idempotente): faltando slots → `incomplete` (não anuncia); slots mínimos + cobertura não confirmada → `hitl_required`. Nunca volta a `policy_selection_pending`.

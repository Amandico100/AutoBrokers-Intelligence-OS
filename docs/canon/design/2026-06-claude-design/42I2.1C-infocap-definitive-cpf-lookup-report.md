## 1. Contrato real confirmado (probe da Resulta)
- **CPF:** `GET /cliente_cpf?codfil=1&cpf_cnpj=<digits|fmt>` → `{ header, cliente: [ { codfil, codigo, nome, ativo, cpf_cnpj, ... } ] }` (`array_key="cliente"`, `result_count=1`). **Só campos de cliente — NÃO há apólice** (`numapo`/`nosnum`/`apolice` ausentes).
- `/busca_cpf` → 200 mas `cliente` vazio (`result_count=0`). `/producao?texto=<cpf>` → **500**.
- **Nome:** `/lista_clientes?texto=` → `{ header, clientes: [ { codigo, nome, ddd, numero } ] }` (amplo: 44–141 resultados) — só fallback.

**Conclusão:** `/cliente_cpf` prova **cliente localizado**, não apólice/cobertura. Não dá para afirmar cobertura só por achar o cliente.

Sem implementação InfoCap funcional no repo (Agent OS legado não sincronizado; o worktree `hotfix-runtime-bundle` não está acessível neste ambiente). Seguimos pelo resultado do probe.

## 4. Endpoint CPF definitivo
`/cliente_cpf?codfil=1&cpf_cnpj=<digits>` (default). Overrides por `connection_config` **sem mexer no banco-schema** (são dados jsonb): `infocap_cpf_search_path`, `infocap_cpf_search_param`, `infocap_search_extra_params`, `infocap_codfil`. O default da Resulta funciona sem alterar nada.

## 5. Como diferenciei client_found de policy_found
Após o registro único, verifico campos de apólice (`numapo`/`nosnum`/`apolice`/`num_apolice`):
- **com** apólice → `found` (`verified_by_connector` + `coverage_evidence`).
- **sem** apólice (caso `/cliente_cpf`) → **`client_found`**: `verification_status` continua `unverified`, **sem** `coverage_evidence`, **sem** `policy_evidence_ready`, `policy_source` **não** vira `connector`, corredor **não** avança. `next_step`: *"Cliente localizado na InfoCap. Próximo passo: buscar apólices/documentos vinculados antes de confirmar cobertura ou acionar assistência."*

## 6. Policy discovery prep (refs sanitizadas)
Do cliente, exponho **apenas**: `codfil`, `codigo` (+ flags `ativo`/`vigente`, e `cidade`/`estado` se úteis). **Nunca** CPF/nome/email/telefone. Diagnóstico inclui `infocap_client_found:true`, `client_ref_available`, `client_ref_fields`, `client_ref`, `next_possible_endpoints:["/cliente","/documento","/producao"]`. **Não** executei chamada de detalhe — a doc não deixa claro qual endpoint lista as **apólices de um cliente** por `codigo/codfil` (`/documento` exige `nosnum`; `/producao` deu 500). Isso fica para o **42I2.1D** (probe de descoberta de apólices).

## 7. policy-lookup route
Trata `found` (persiste verified), `client_found`/`policy_lookup_pending` (persiste next_step seguro + metadata sanitizada, **sem** cobertura/avanço), `multiple_matches`, `not_found`, `auth_error`, `provider_error`. Mock/manual **inalterados**.

## 8. Segurança / logs
Backend loga só `company`, `connection`, `endpoint` (mascarado), `status`, `result_count`, `duration_ms`. Sem CPF/nome/email/telefone/token/segredo/payload. Respostas e diagnostics sem PII crua (só refs `codfil`/`codigo` + flags).

## 9. Como testar (console, logado; backend deployado + conexão ready)

console.log(det.case.verification_status, det.case.policy_source, det.case.metadata?.attendance_macro_state, det.case.next_step);

Próximo passo: buscar apólices/documentos…". **`/busca_cpf` não é mais default.** **mock** continua funcionando. **not_found** não confirma cobertura.

## 10. Já é possível ler apólice? **Ainda não**
`/cliente_cpf` só dá o cliente. Para trazer apólice/cobertura é preciso descobrir o endpoint que **lista apólices por cliente** (codfil/codigo) — alvo do **42I2.1D**.

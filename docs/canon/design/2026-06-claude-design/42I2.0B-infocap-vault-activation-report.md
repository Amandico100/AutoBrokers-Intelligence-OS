> **Status:** concluído (parcial por bloqueio justificado) · typecheck verde · build verde · `git diff --check` limpo · **só TS/Next no Web** (sem SQL/schema/migrations, sem backend Python, sem chamada real InfoCap, sem segredo no código/log) · sem deploy automático.
> **Data:** 2026-06-15 · **Modelo:** Claude Opus 4.8 · **Branch:** main

## 1. Resumo executivo / decisão
A diagnostics mostrou `status: draft`, `ready_for_real_lookup: false`. Para chegar a `ready=true` faltam **duas** coisas: `base_url` configurado **e** `encrypted_secret_ref` presente (credenciais).
- **`base_url`** é metadado não-secreto → este batch implementa a atualização segura.
- **`encrypted_secret_ref`** exige um **fluxo seguro de segredo** que **ainda não existe** para InfoCap. Conforme o requisito #3 do batch ("se não existir mecanismo seguro, NÃO inventar criptografia, NÃO salvar login/senha em JSON, parar e reportar"), **não** gravei credenciais e **não** forcei `status='connected'`.

Resultado: o setup deixa a conexão em `configuring` com `base_url`, e a diagnostics continua honesta (`ready_for_real_lookup:false`, blocker `missing_credentials`) até o fluxo de segredo InfoCap existir.

## 2. Auditoria — qual é o mecanismo seguro de segredo hoje
O padrão canônico do Vault (visto em `app/api/vault/connections/[connectionId]/whatsapp/configure/route.ts`) é:
1. o Next **recebe** as credenciais e **delega ao backend** `POST /api/whatsapp-integrations/configure` (header interno `X-AutoBrokers-Internal-Key`);
2. o **backend cifra** (via `app/services/encryption_service.py` / `whatsapp/integration_secrets.py`) e **armazena** em `integrations`;
3. o Next atualiza a `tenant_connection` para **referenciar** a integração (`technical_ref_type='integration'`, `technical_ref_id`, `status='connected'`). **O segredo nunca fica no Next.**

**Não existe** equivalente para InfoCap: o `/api/whatsapp-integrations/configure` é específico de WhatsApp/z-api; não há endpoint/serviço que cifre e guarde credenciais genéricas/InfoCap. O Web (lib/app) **não** tem utilitário de criptografia. Portanto, criar `encrypted_secret_ref` de InfoCap com segurança **não é possível** sem um batch de backend.

## 4. Endpoint (criado)
`POST /api/attendance/connectors/infocap/setup` — auth Iron Session (`resolveSessionCompany`), isolado por `company_id`. Body aceito: `{ "base_url": "https://api.corpnuvem.com" }`.
- **Rejeita** qualquer segredo no body (`payloadHasSecret` → 400 `SECRET_REJECTION_MESSAGE`): login/senha/token/api_key/secret.
- Localiza template `infocap` + a `tenant_connection` existente da corretora.
- Atualiza `connection_config.base_url` (merge) e move `status` `draft→configuring` (nunca `connected`, pois sem segredo).
- Audita (`vault_audit_log`, event `connection_configured`, sem segredo).
- Retorna `diagnostics` fresca + `note` explicando o que falta.
**Nunca** retorna `encrypted_secret_ref`, login, senha, token.

**Esperado:** depois do setup → `base_url_configured:true`, `status:"configuring"`, `secret_ref_present:false`, `ready_for_real_lookup:false`, `blockers:["missing_credentials"]`. Enviar segredo no body → **400** (rejeitado).

## 7. O que falta para `ready_for_real_lookup=true` (bloqueio reportado)
Falta **um fluxo seguro de segredo InfoCap** (batch de backend), espelhando o WhatsApp:
- **Endpoint backend** novo, ex.: `POST /api/connectors/infocap/configure` (ou genérico `/api/vault/secrets/store`) que receba `company_id` + `connection_id` + `login`/`senha`, **cifre** via `encryption_service.py` e **armazene** (em `integrations` ou tabela/coluna de segredo do Vault), retornando uma **referência**.
- O Next (setup) então grava `encrypted_secret_ref` = referência + `status='connected'` (sem nunca tocar no segredo cru).
- Tabela/coluna: reusar `integrations` (como WhatsApp) **ou** definir armazenamento de segredo para `tenant_connections.encrypted_secret_ref` (decisão do Architect; pode exigir migration → fora deste escopo).
Sem esse endpoint, gravar `encrypted_secret_ref` no Web seria inventar criptografia / salvar segredo cru — proibido.

# 42X3.1 — Registry-Aware Action Plan & Execution Alignment Report

> **Status:** concluído · testes offline **558 verdes** (32 alignment + 61 registry + 42 outbox + 31 execution + 42 engine + 350 anteriores) · `typecheck` EXIT=0 · build verde · **sem schema novo** · **NENHUM envio real** (`send_allowed=false` · `canSendReal=false` · `send_real_allowed=false`) · **sem PII / destino mascarado**.
> **Data:** 2026-06-17 · **Modelo:** Claude Opus 4.8 · **Branch:** main

## 1. Qual era a divergência
No 42X3, só o `action-outbox/prepare` consultava o Insurer Channel Registry. O `action-plan` continuava montando `ChannelAvailability` apenas a partir de `human_support_destinations`, então:
- **Action Plan** selecionava `human_broker_manual`;
- **Execution Session** nascia `human_broker_manual` (canal do plano);
- **Outbox** usava `zapi`/`meta`/`evolution` pela config.
O teste live confirmou: `ACTION PLAN.selected_channel = human_broker_manual` enquanto `OUTBOX.provider = zapi`. Plano/execução e outbox falavam **canais diferentes**. O 42X3.1 alinha os três na mesma config.

## 2. Como o Action Plan agora usa o registry
`action-plan/route.ts` resolve a config ativa mais específica (`resolveActiveInsurerChannelConfig`) por `insurer_key`/`corridor_key`/`subcorridor_key`, monta um `PlanChannelConfig` (lite: `config_id`, `provider_key`, `provider_label`, `channel`, `destination_ref_masked`, `homologation_status`) e o passa a `buildExternalActionPlan({ activeChannelConfig })`. O engine, quando há config, **dita o canal** (mapeando `manual`→`human_broker_manual`), enriquece o candidate correspondente (`provider_key`/`config_id`/`destination_ref_masked`/`homologation_status`/`current_mode: dry_run`) e preenche os campos `selected_*` + `channel_config_source`. Sem config → fallback `human_broker_manual` (`channel_config_source: 'fallback_manual'`). O `selected_provider_payload` é montado pela rota via `buildProviderPayload` a partir do draft.

## 3. ExternalActionPlan enriquecido
Novos campos (sanitizados): `selected_config_id`, `selected_provider_key`, `selected_provider_label`, `selected_destination_ref_masked`, `selected_homologation_status`, `selected_provider_payload`, `channel_config_source` (`registry|fallback_manual|none`). Cada `ChannelCandidate` ganhou `provider_key?`/`config_id?`/`destination_ref_masked?`/`homologation_status?`.

## 4. Como a Execution usa o provider
`startExecutionSession` deriva o `adapter` do `plan.selected_provider_key` via `providerSandboxAdapterId`: `zapi`→`zapi_sandbox`, `evolution_go`→`evolution_go_sandbox`, `meta_cloud`→`meta_cloud_sandbox`, `manual`/sem provider→`human_manual_sandbox`. O `channel` e o `prepared_message` vêm do plano. `external_action_sent` permanece `false`.

## 5. Como o Outbox reutiliza a config
`action-outbox/prepare` agora **prioriza** a config já resolvida no plano (`selected_config_id`/`selected_provider_key`/`selected_destination_ref_masked`/`selected_provider_payload`/`selected_channel`). Só re-resolve no registry se o plano não trouxer config (planos antigos) — e, nesse caminho, se o canal resolvido divergir do `plan.selected_channel`, registra o warning **`channel_plan_outbox_mismatch`** (na resposta + auditoria). No fluxo normal (plano com config), **não há mismatch**.

## 6. Como o fallback manual continua
Sem config ativa para a seguradora/corredor/subcorredor, `resolveActiveInsurerChannelConfig` devolve `null`, o plano cai em `human_broker_manual`, a execução usa `human_manual_sandbox` e o outbox idem — comportamento idêntico ao pré-42X3, preservando todos os goldens.

## 7. Como Z-API / Evolution Go / Meta entram sem mudar o engine
A escolha de provider está 100% na **config do admin** + no **registry**. O engine só recebe um `PlanChannelConfig` lite e um `provider_key`; os adapters sandbox e os payload builders são por provider. Trocar de provider = trocar a config — **zero mudança no Action Engine**. Os tipos do engine não importam o registry (evita acoplamento e mantém os testes Node `.mjs`).

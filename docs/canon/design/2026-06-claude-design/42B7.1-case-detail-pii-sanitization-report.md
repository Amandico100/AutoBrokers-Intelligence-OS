## 2. Como sanitizou o `case`
`safeCaseDetail(caseRow)`: remove `insured_document_ref` cru e adiciona:
- `has_insured_document_ref: boolean` (true se houver documento com ≥11 dígitos);
- `insured_document_masked: string|null` (ex.: `***09 (len=11)`).
Mantém todos os campos operacionais (`status`, `verification_status`, `policy_source`, `policy_number`, `policy_snapshot`, `coverage_evidence`, `metadata`, etc.). Aplicado no GET e no PATCH.

## 3. Como sanitizou as `messages`
`sanitizeMessageForDetail(message)`: mascara CPF/CNPJ e sequências longas de dígitos no `content` (regex `\d[\d.\-/\s]{9,}\d` → `"[documento omitido]"`), preservando `id`, `role`, `created_at`, `type`. Aplicado a todas as mensagens do GET detail. **Não altera o banco** — só a resposta.

## 4. Impacto na UI
- `AttendanceConversationSimulator`: a condição do botão "Simular consulta de apólice" usava `c.insured_document_ref`; agora usa `c.has_insured_document_ref` (preservando o mesmo comportamento). O simulador nunca exibia o documento — continua sem exibir; pode usar `insured_document_masked` no futuro se necessário.
- `CaseDetailClient`: não usava `insured_document_ref`; sem impacto. As mensagens exibidas no detalhe agora aparecem com CPF mascarado.

## 5. PATCH
`PATCH /api/attendance/cases/[caseId]` também passa por `safeCaseDetail` na resposta.

## 6. Goldens atualizados
No `scripts/attendance-golden-tests.mjs`, após enviar o CPF, é feito `GET /api/attendance/cases/[id]` e os asserts:
- `detail.case` **não** tem `insured_document_ref`;
- `detail.case.has_insured_document_ref === true`;
- o JSON do detail **não** contém o CPF (formatado `123.456.789-09` nem dígitos `12345678909`);
- nenhuma `messages[].content` expõe o CPF cru.
Helper `containsCpf()` reforça os asserts de runtime (`noCpfExposed`) para pegar também o CPF formatado. Documentado que o **banco pode guardar** o documento, mas o **payload do dashboard não expõe cru**.

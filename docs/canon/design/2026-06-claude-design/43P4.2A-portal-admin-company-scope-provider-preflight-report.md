## 2. O que mudou (código)
### Escopo de company (multi-tenant)
- **`lib/attendance/portal-company-scope.ts` (novo, PURO/self-contained):** `resolvePortalCompanyScope(input)` decide o tenant com precedência:
  1. sessão já vinculada a uma company (tenant **travado** — ignora override);
  2. **master admin** com `company_id` solicitado e **válido** → usa o escolhido;
  3. `users_v2.company_id` do próprio usuário;
  4. **única** company existente (piloto single-tenant).
  Admin sem escopo resolvível → `company_scope_required=true` (não adivinha). Usuário comum **nunca** escolhe tenant via header/cookie.
- **`lib/attendance/portal-admin-context.ts`:** `getPortalAdminContext` agora lê o escopo solicitado do header `X-AutoBrokers-Company` **ou** do cookie `aj_company`, valida no banco que a company existe, e delega a decisão à função pura. Retorna `{ companyId, userId, isMaster, company_scope_required }` (campos novos aditivos; rotas existentes seguem só checando `companyId`). Novo helper `listCompaniesForAdmin` (id/nome/status; sem dados sensíveis).
- **`app/api/admin/portal-browser/companies/route.ts` (novo, GET):** lista corretoras p/ o seletor; só admin autenticado; sanitizado.
- **`app/admin/portal-browser/page.tsx`:** seletor "Corretora (tenant)" aparece p/ master admin ou quando há >1 company; ao escolher, grava cookie `aj_company` e recarrega — **todas** as chamadas passam a operar no tenant escolhido (cookie vai automático em toda requisição same-origin, sem alterar nenhum fetch).

> **Por que cookie + header (e não tocar 24 rotas):** o cookie `aj_company` é enviado automaticamente em toda chamada same-origin, então o fix vale para **todas** as rotas de portal sem editar cada uma. O header continua suportado para chamadas programáticas. A segurança não depende do cliente: a decisão é server-side e **só** aceita override quando `is_admin && !session_company`.

### Falso-positivo de leak
- Blockers renomeados em `lib/attendance/browserbase-real-adapter.ts`: `browserbase_key_env_missing`, `browserbase_project_env_missing`. Teste atualizado + nova asserção garantindo que os blockers **não** contêm a string literal do env.

## 4. Provider Strategy Preflight (decisão de arquitetura — sem implementar)
Mantemos arquitetura **provider-agnostic** (Provider Registry já existe: `browserbase|local_playwright|stagehand|skyvern_lab|mock`). Recomendação:

| Provider | Papel recomendado | Nota |
|---|---|---|
| **browserbase** | Canary + produção inicial | Infra cloud, live view, observabilidade, compatível com Playwright/CDP. Free p/ canary; Developer US$20/mês quando repetir. |
| **local_playwright** | Dev/testes baratos | Sem custo de serviço; bom p/ CI/local; sem infra cloud/anti-bot. |
| **browserless_self_hosted** | Avaliar p/ reduzir custo no futuro | Docker + fila + debug viewer; exige licença comercial/ops. |
| **stagehand** | Camada de inteligência (não-infra) | "Cérebro" sobre Browserbase/Playwright; não substitui o browser. |
| **browser_use** | Agente exploratório (lab) | MIT; o próprio projeto recomenda cloud p/ produção/stealth. |
| **skyvern_lab** | Lab p/ fluxos muito difíceis | Pesado, AGPL-3.0; não como motor principal do MVP. |

**Conclusão:** Browserbase Free → Developer é o caminho mais rápido e menos arriscado p/ canary/produção inicial; manter `local_playwright` p/ dev; não ficar refém de um vendor. **Nenhum provider novo implementado neste batch.**

### Custo Browserbase (resumo p/ o Founder)
- "Browser hour" = tempo de browser **aberto** (não nº de corretoras). Cadastrar 100 corretoras = **0** se ninguém executar.
- Free: 3 browsers concorrentes, 1 browser hour, 15 min/sessão — **suficiente p/ o 1º canary de login**.
- Developer US$20/mês: 25 concorrentes, 100 browser hours (~3.000 tarefas curtas), excedente US$0,12/h.
- Startup US$99/mês: 100 concorrentes, 500 browser hours — só quando várias corretoras usarem portal de fato.
- **Recomendação:** não pagar agora; usar Free no canary; migrar p/ Developer quando repetir.

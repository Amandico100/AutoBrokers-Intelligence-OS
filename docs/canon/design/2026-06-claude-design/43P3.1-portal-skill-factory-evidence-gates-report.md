## 1. Como evitamos skills inventadas
Skill deixa de ser texto solto: agora **toda skill nasce de um Blueprint + Evidence Pack + Quality Score**. Sem evidência (catálogo oficial + map + dry-run/trace/replay), a skill não passa de `draft_needs_evidence`/`draft_ready_for_dryrun`; sem trace/replay de um dry-run real do sandbox, **nunca** vira `sandbox_validated_candidate`; e `approved_future` continua bloqueado nesta fase. Seletores/ações não saem do improviso: vêm do Portal Map e dos `allowed_actions`/`forbidden_actions` do blueprint.

## 2. Quais blueprints existem
`lib/attendance/portal-skill-factory.ts` (genéricos, não específicos de seguradora): `login_check`, `policy_query`, `billing_query`, `status_query`, `document_download_dryrun`, `assistance_opening_dryrun`, `claim_notice_dryrun`. Cada um define journey, `objective_template`, `required_evidence`, `required_inputs`, `allowed_actions`, `forbidden_actions` (sempre incluindo bypass/real/credencial), `expected_outputs`, `recommended_map_pages`, `challenge_policy: hitl_required`, `min_quality_score` e `promotion_rules`. Uma skill concreta = instância de um blueprint com `portal_id`/`map_id`.

## 3. Como o Evidence Pack funciona
`PortalSkillEvidencePack` reúne `official_sources`, `confidence`, `audience`, `journey`, `portal_status`, `portal_map_id`, `trace_id`, `replay_id`, `human_review_status`, `missing_evidence[]` e `evidence_score` (0–100). `buildPortalSkillEvidencePack` deriva tudo da entrada do **catálogo global** (43P1.2) + map + refs de dry-run. `validateSkillEvidencePack` exige no mínimo portal/official_sources/confidence/journey. `explainMissingEvidence` traduz lacunas em texto para o admin. **Sem credencial/PII.**

## 4. Como o Quality Score funciona
`evaluatePortalSkillQuality(skill, evidencePack, lastRun?)` → 0–100 com pesos: evidência (até ~50: official+confidence+audience+journey+map), skill/forbidden (até 15), execução (até 30: dry-run passed + trace + replay), revisão humana (5). Tiers: `<60 draft_needs_evidence`, `60–79 draft_ready_for_dryrun`, `80–94 sandbox_validated_candidate`, `95–100 production_candidate_future` (**sem `approved_future` aqui**). Regra dura: **sem trace+replay+dry-run passed, não passa de draft** (`safe_to_promote_to_sandbox_validated=false`). Challenge não resolvido ou ação proibida detectada viram blockers.

## 5. Quais candidatos aparecem do catálogo global
`generatePortalSkillCandidatesFromCatalog(catalog, filters)` percorre as 189 superfícies (43P1.2) e gera candidatos `{ owner_key, portal_id, journey, blueprint_key, reason, risk_level, evidence_score, suggested_next_step }`, ordenados por **menor risco + maior evidência**. Filtros: `audience`, `status`, `confidence`, `exclude_mfa_captcha`, `journeys`. Risco: certificado→`high`, MFA/captcha/OTP→`medium`, senão `low`. Candidatos `low` recebem `instantiate_skill_and_dry_run`; os de risco, `review_challenge_before_dry_run`.

## 6. Score da skill Allianz login atual
`allianznet_corretor_login_check_v1` com Evidence Pack (catálogo: official_sources + `confidence=confirmed` + audiência corretor + journey login + map v1) tem **evidence_score 85** (sem trace/replay). No Quality Score: **sem run → `draft_ready_for_dryrun`** (não promovível, falta trace/replay). **Com um dry-run completo (passed + trace + replay) → score ~95 → `production_candidate_future`** e `safe_to_promote_to_sandbox_validated=true`. Ou seja: a estrutura confirma que a skill atual é forte (85→95) e explica exatamente o que falta para subir de nível (rodar dry-run + revisão humana).
